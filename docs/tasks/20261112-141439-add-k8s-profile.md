# Add K8s Profile Context Management

Created: 2026-11-12 14:14:39 -0800

## Objective

Add an installable `k8s-profile` tool and its tool-specific library to manage local Kubernetes contexts, following `git-profile` terminology and interactive UX.

Required actions:

- `create`: prompt for mandatory `name`, `server`, and `token`, then register the cluster, credentials, and named context in local kubectl configuration.
- `list`: load profiles from `kubectl config view`, not a separate saved-profile registry.
- `update`: select an existing profile and update its server and/or token.
- `delete`: select and confirm deletion of an existing profile, with safe cleanup of its owned configuration and credentials.

## Scope And Behavioral Contract

- New executable: `tools/bin/k8s-profile`.
- Tool-specific modules: `tools/lib/picotools/k8s-profile/`, installed as `lib/picotools/k8s-profile/`. Reuse shared helpers from `lib/picotools/`; do not introduce a generic profile framework or rewrite `git-profile`.
- New Bats coverage: `tests/k8s-profile*.bats` and `tests/helpers/k8s-profile.bash`.
- Documentation, test dependencies, and installed-layout checks: `README.md`, `package.json`, `.tool-versions` if needed, and `.github/workflows/test.yml`.
- A profile is one Kubernetes context. Kubeconfig is authoritative; list all contexts visible to kubectl, including contexts created outside this tool, and preserve their exact names.
- Use `k8s-profile [--debug] <command>`. The four required commands take no command-specific arguments and use interactive prompts/selection where applicable, matching `git-profile`. Support its help/version aliases and global-only `--debug`; reject unsupported arguments before prompting or writing.
- Use “profile” in menus and summaries, “context” when explaining kubectl configuration, and “Token” rather than GitHub-specific “PAT”. Reuse shared section/step/summary, numbered/arrow-key selection, and table helpers.
- Creating/updating a profile must not silently activate another context. For deletion of the current context, explicitly warn before confirmation, clear the obsolete current-context reference on success, and never select a replacement silently.
- Names are stable profile identities, as in `git-profile`; context renaming, `read`, `set`, token-printing, namespace editing, and optional CA/TLS prompts are not required in this first implementation.
- Operations manage local configuration only: no cluster connectivity check, credential-plugin execution, token validation request, or remote resource mutation. Do not disable TLS verification automatically. Document that name/server/token-only creation relies on the API server's certificate being trusted.
- Inspect concurrent changes before implementation and preserve unrelated work. Sequence tasks below because they share the new entrypoint, modules, and tests.

### Task K8S-01: Establish Safe Kubeconfig And Credential Mutation Contracts

Status: completed

Assigned: DESIGN-01 subagent; coordinator records its verified findings here.

Kind: investigation

Priority: P1 — resolve file ownership, shared entries, and token handling before implementing writes.

Dependencies: none

Primary ownership:

- Design findings recorded in this task document.
- Isolated kubeconfig probes/fixtures for later `tests/k8s-profile*.bats` coverage.

Finding:

Kubeconfig contexts reference independently named cluster/user entries that can be shared or spread across files. `set-credentials` merges existing authentication fields, and passing `--token` would expose a secret in process arguments. The repository has no existing adapter for these boundaries.

References:

- `tools/bin/git-profile:422-464` (`save_context_and_token`), `466-561` (`create_context`).
- `tools/lib/picotools/git-profile/profile.sh:428-579` (candidate publication and snapshot/restore).
- Official kubectl references linked under Analysis Coverage And Baseline.

Requirements:

1. Use real kubectl against disposable fixtures only. Establish read/write targets for the default configuration, single-file `KUBECONFIG`, multi-file `KUBECONFIG`, absent files, duplicate/shadowed names, and entries whose context/cluster/user live in different files. Preserve kubectl's loading semantics; never flatten the chain into a live file.
2. Record deterministic context-to-cluster/user naming and ownership rules. Do not assume the three names are equal or infer ownership from a name prefix alone. Define collision handling and how mutations of externally created/shared entries are isolated or rejected with an actionable error before any write.
3. Select and demonstrate a token-safe persistence mechanism, such as a private staged kubeconfig or a private token file referenced by kubeconfig. Do not pass tokens through kubectl/jq process arguments, environment variables, command previews, or logs. A separate token file is permitted; a separate authoritative profile registry is not.
4. Define preflight, staging/publication or rollback, permission enforcement, and cleanup for every affected file. Preserve unrelated fields, relative certificate/key references, and other contexts. Reject unsafe write targets rather than following symlinks or modifying linked/non-regular files blindly.
5. Define behavior for incompatible existing authentication methods, shared-entry updates, owned-orphan cleanup, current-context deletion, and configuration changes between selection and mutation. Avoid leaving stale token/exec/basic-auth combinations or overwriting newer external changes during recovery.

Acceptance criteria:

- Append evidence-backed decisions here, including chosen naming/ownership, token persistence, write-target selection, and failure/recovery strategy.
- Isolated probes demonstrate single- and multi-file behavior without reading the developer's real configuration, contacting a cluster, or invoking credential plugins.
- All boundaries above have a testable outcome. If safe multi-file mutation or a required behavior cannot be delivered, record the exact blocker and obtain a maintainer decision before K8S-02 starts; do not silently narrow the requirement.

Verification: review recorded probe commands, kubectl version, redacted results, and before/after fixture comparisons. Any saved fixtures use only synthetic data and repo-relative paths; scrub local absolute paths and session identifiers from evidence.

Verified design decisions (DESIGN-01):

- Probed with kubectl `v1.37.2` (linux/amd64) and jq `1.8.2`, using disposable HOME/KUBECONFIG/XDG fixtures and `KUBECTL_KUBERC=false`. Resolve test executables before isolating HOME; otherwise asdf shims can fail with exit `126`/`127`.
- Empty/unset `KUBECONFIG` uses the isolated default; separator-only chains are empty, not the default. Deduplicate repeated identical paths, retain loading precedence, and reject distinct path aliases to one physical file for mutation. New entries target the first existing chain member, otherwise the last member; existing profiles target their visible context's origin file.
- Across files, first definitions win as whole objects. Track every physical definition/reference, including shadows. Refuse deletion when the selected context has multiple definitions, since deleting only the visible one would expose a shadow.
- Allocate managed resources as `k8s-profile:<exact-context-name>:cluster:<n>` and `k8s-profile:<exact-context-name>:user:<n>`, taking the lowest unused positive generation across all physical files. Add a `picotools.k8s-profile` extension containing `version: 1`, `profile`, and the `context`, `cluster`, or `user` role. Reuse/delete only when explicit metadata and naming agree; never infer ownership from a prefix. Unsupported reserved ownership metadata fails safely.
- Reuse only unambiguous, exclusively referenced owned resources in the selected context's file. Otherwise clone changed cluster/user state into that file under fresh names. Preserve other contexts and shared/unmanaged resources. Owned orphan cleanup scans all physical contexts and joins other eligible origin files to the transaction when needed.
- Store tokens inline in managed user stanzas. Write an unexported token with Bash builtin output to a private input file and use `jq --rawfile`; never use token-bearing process arguments/environment variables. Disable xtrace and capture all kubectl/jq stderr privately: nonraw view still exposes some exec/provider fields, and malformed duplicate-user errors can include credentials. List only an explicitly selected nonsecret projection.
- Server-only update preserves existing authentication. Token add/replace rejects exec/provider/basic/certificate authentication rather than silently changing mechanisms; bearer `tokenFile` is compatible, but replacement writes inline `token` and removes only the reference. Never open/delete external token files, certificates, or keys.
- Missing references stay visible. Supplying the missing Server/Token can create the corresponding resource; reject a proposed change lacking required cluster information. Existing-name overwrite is default-no and uses the same isolated mutation engine while retaining unrelated context/TLS data.
- Stage explicit per-file raw JSON, never a merged view. Recognised kubeconfig fields/extensions are preserved semantically; kubectl may reorder/omit defaults and drops unknown non-schema fields, so comments/formatting/unsupported fields are not preservation guarantees. When cloning between directories, rebase relative CA/certificate/key/token-file references against their original loading directory without opening, flattening, embedding, or resolving the referenced files.
- Create/update preserve all current-context values. For current-profile deletion, warn and clear every nonempty current-context in the chain, including hidden different values, from lowest precedence toward highest; never activate a fallback. Noncurrent deletion clears only obsolete references to the deleted name and preserves the effective current profile.
- Add tool-local ordinary required/default prompts that observe read failures; completed blank input can retry, but EOF must fail without applying a default. The shared secret prompt already terminates required-input EOF. No shared prompt rewrite is required.
- Snapshot the chain and path/content/identity state before prompts, recheck afterward and around staging, reject nonregular/linked/symlink/foreign-owned unsafe write targets, and use private backups/candidates. Acquire exclusive existing-compatible `.lock` files for the write-set in deterministic order, never deleting a pre-existing lock.
- Stage/validate all candidate files and the substituted chain before publication. Publish same-directory mode-`0600` candidates; newly absent targets need atomic no-replace publication. On returned failure/handled signals, recover in reverse only while a live file still matches the published candidate. Do not overwrite newer external edits: retain private backups plus a nonsecret recovery manifest and report incomplete recovery.

Completion evidence:

- Real-kubectl probes confirmed default/single/multi-file targeting, absent/repeated/relative paths, shadows, split origins, hidden current-context fallback, lock behavior, semantic raw-JSON preservation, and no credential-plugin execution.
- A token-safe single-file candidate prototype preserved neighbouring/shared/current/context/TLS/auth state, skipped unmanaged name collisions, rebased relative CA meaning, published mode `0600`, rejected symlinks/hardlinks/unsafe parents, and left no candidate/token/lock files after success.
- A two-file prototype demonstrated current-reference clearing and successful deletion, restoration after injected second-publication failure, and refusal to overwrite a newer external edit during recovery.
- Probe driver command families: `kubectl config view -o json`, explicit per-file `config view --raw --merge=false -o json`, nonsecret config setters, `config delete-context`, `config unset current-context`, and client-version output. Disposable Bash syntax checks and `git diff --check` passed. Probe artifacts are private disposable execution evidence, not committed fixtures.
- Residual limitations to document/test: cross-file publication is not atomically visible; locks protect cooperative writers but cannot eliminate the final Bash check/rename race; SIGKILL/power loss may leave partial state/locks/private recovery artifacts. No crash-atomic guarantee or automatic recovery over newer data is promised. No prerequisite blocker remains.
