Status: completed (2026-11-13, local implementation session)

Finding: the CLI accepts only create/list/update/delete; creation registers a
context without activation. Users currently have to switch separately using
kubectl. The existing transaction engine already provides isolated snapshots,
checked publication, stale-state detection, locking, and failure recovery.

Requirements:

1. Accept one optional nonempty, exact existing context name; without it, reuse
   the checked sorted profile-selection menu. Cancellation/invalid input must
   not switch, and selection must be rechecked for stale state. Support external
   names without applying the create-only naming restriction; reject lossy
   UTF-8 argument conversion and multiple physical context definitions.
2. Set only `current-context` in the first existing chain file, retaining lower
   fallbacks and every resource/reference. Already-effective selection is a
   byte-preserving no-op after stale-state rechecking.
3. Reuse the transaction engine and verify both merged state and raw physical
   state before publication. Retain all existing safety/encoding restrictions.
4. Never make cluster requests, execute credential plugins, read external
   credential files, or expose credentials. Tests must isolate all runtime
   HOME/KUBECONFIG/XDG/TMPDIR state with synthetic credentials only.
5. Update help/README and the real archive-installed smoke together.

Acceptance criteria:

- Independent kubectl reads confirm the requested current context and unchanged
  resources, TLS/auth/namespace/extensions, and lower-priority chain files.
- Unknown/shadowed/invalid argument names, unsafe paths, locks, stale state,
  corrupted candidates, returned failures, and handled signals fail safely.
- Omitted-name selection works in arrow-key and redirected numbered terminal
  modes, restores terminal state, and safely refuses cancellation/empty names.
- Focused/full tests, package gates, pre-commit, and installed smoke pass.
